# Пополнение ТЗ

Применяй, когда владелец присылает дополнение к ТЗ, ответ заказчика на открытый вопрос,
отмену или изменение требования. Цель — чтобы новое требование попало во все документы
и ничего уже решённого не сломалось молча.

По умолчанию это отдельный PR только с документами (ветка `docs/req-<YYYY-MM-DD>-<slug>`).
Реализация идёт следующими задачами из roadmap, если владелец не попросил сделать всё сразу.

## 1. Сохрани первоисточник

Положи текст как есть в `docs/client-input/YYYY-MM-DD-<slug>.md` по шаблону из
[docs/client-input/README.md](../../../docs/client-input/README.md) и добавь строку в список там же.
ПДн, ключи и пароли замени на `[удалено]`. Если в тексте были ключи, скажи владельцу, что
их нужно перевыпустить и передавать через env.

## 2. Разбери на атомарные изменения

Для каждого пункта определи тип:

| Тип | Пример |
|---|---|
| новое требование | «добавьте вывод средств на карту» |
| изменение существующего R-NN | «рефералка двухуровневая» |
| отмена R-NN | «VPN не нужен» |
| ответ на открытый вопрос Q-NN | «процессинг — такой-то» |
| уточнение без изменения объёма | «Premium называется Pro» |

Неоднозначный пункт не толкуй в свою пользу. Запиши варианты и перейди к шагу 6.

## 3. Оцени влияние

По каждому пункту проверь:

- `docs/requirements.md` — есть ли похожее требование, нет ли противоречия;
- `docs/decisions.md` — не противоречит ли принятым решениям, не отвечает ли на Q-NN;
- `docs/roadmap.md` — какие задачи затронуты, особенно уже готовые (✅) и в работе (🟨);
- `docs/architecture.md` — нужна ли новая таблица, модуль, адаптер, фоновая задача;
- правила M1–M13 в `AGENTS.md`. Требование, которое их нарушает (например, «разрешить
  минусовой баланс»), не вносится без явного решения владельца;
- код — если затронута уже сделанная задача, найди, что именно придётся переделать.

## 4. Обнови документы

- `requirements.md`: новое требование получает следующий свободный `R-NN`. Изменённое —
  новая формулировка, статус «изменено», старая формулировка сохраняется в истории. Отменённое —
  статус «отменено», строка не удаляется. Заполни «Источник» и «Задачи». Добавь строку в
  «Историю изменений ТЗ».
- `decisions.md`: ответ на Q-NN — новое решение D-NNN со ссылкой на источник, в строке вопроса
  пометка «закрыт → D-NNN». Если ответ расходится с допущением, на котором уже построен код,
  это отдельный пункт влияния (шаг 5).
- `roadmap.md`:
  - новая работа — новая задача `T-NN` с описанием и DoD в нужном этапе;
  - изменение ещё не начатой задачи — правь её описание и DoD;
  - изменение готовой или начатой задачи — **новая задача на доработку**, старую не переписывай;
  - отменённое требование — задача получает пометку «отменена» со ссылкой на R-NN.
- `architecture.md`, `glossary.md` — если появились новые сущности, потоки или термины.
- `docs/partners/README.md` — если назван поставщик.

## 5. Проверь согласованность

- У каждого действующего R-NN есть хотя бы одна задача, у каждой задачи этапа — требование.
- Нет противоречий между requirements, decisions и architecture.
- Этапы в requirements.md и roadmap.md совпадают.

## 6. Вопросы

Вопрос владельцу задавай сразу, только если без ответа нельзя корректно записать требование:
противоречие с правилом M, конфликт с уже сделанным, два несовместимых толкования.
Остальное записывай в открытые вопросы `Q-NN` с допущением «до ответа».

## 7. PR и отчёт

Описание PR по шаблону. В разделе «Что сделано» дай таблицу влияния:

| Пункт | Тип | R / Q | Задачи | Переделка готового |
|---|---|---|---|---|

В ответе владельцу кратко: что добавлено, что изменилось в плане и сроках, что придётся
переделать, какие вопросы нужно передать заказчику.
