# backend/AGENTS.md

Правила кода backend. Общие правила, включая правила для денег M1–M13, — в [../AGENTS.md](../AGENTS.md).

## Запуск и проверки

Из корня: `make dev-backend`, `make backend-lint`, `make backend-typecheck`, `make backend-test`.
Из `backend/`: `uv run pytest -k name`, `uv run mypy`, `uv run ruff check --fix .`.
Для тестов нужен PostgreSQL из `DATABASE_URL`. Тестовая БД (`<db>_test` или `TEST_DATABASE_URL`)
пересоздаётся при каждом запуске pytest.

## Устройство приложения

- `app/config.py` — `Settings` (pydantic-settings). Это единственное место, где читаются env
  (тест `test_env_is_read_only_in_config`). Секреты объявляются как `SecretStr`.
  В коде настройки берутся через `get_settings()` или `request.app.state.settings`.
- `app/main.py::create_app(settings)` — фабрика. В тестах приложение создаётся с тестовыми
  настройками, глобального состояния нет.
- `app/db.py` — `Base` (все модели наследуют его), `get_session` (сессия на запрос).
- `app/models.py` — импортирует модели всех модулей. Новую модель обязательно добавляй сюда,
  иначе Alembic её не увидит.
- Инфраструктурные эндпоинты (`/health`) лежат в корне, бизнес-API — под `/api/v1/<module>`.

## Бизнес-модуль

```
app/modules/<name>/
  models.py    SQLAlchemy-модели (Mapped[...], mapped_column), без бизнес-логики
  schemas.py   Pydantic-схемы запросов и ответов API
  service.py   бизнес-логика и границы транзакций; принимает AsyncSession первым аргументом
  router.py    тонкий слой FastAPI: зависимости, вызов сервиса, маппинг ошибок в HTTP
  errors.py    доменные исключения модуля (по мере надобности)
tests/modules/<name>/test_*.py
```

- Роутер не содержит логики и запросов к БД. Сервис ничего не знает про HTTP (никаких
  `HTTPException` в сервисе).
- Модули общаются через функции `service.py` друг друга, а не через чужие модели напрямую.
  Исключение — чтение для админки и отчётов.
- Зависимости без циклов: `ledger` ни от кого не зависит, остальные зависят от него.
- Не создавай слой репозиториев и базовые классы «на будущее». Запросы пиши в сервисе.

## Транзакции и блокировки

- Сессия на запрос открывается `get_session`. Сервис, выполнивший запись, сам делает
  `await session.commit()` в конце бизнес-операции. При исключении изменения откатываются
  при закрытии сессии.
- Функции ledger (`post_transaction` и т. п.) **не делают commit**: они работают внутри
  транзакции вызывающего кода, чтобы проводки и связанные записи (заказ, подписка, аудит)
  фиксировались атомарно.
- Во время открытой транзакции нельзя ходить во внешние сервисы (M6).
- Блокировки: `select(...).with_for_update()`, строки блокируются в порядке возрастания id.

## Модели и БД

- Первичные ключи — `UUID` (`uuid.uuid4`, генерируется в приложении). Время — `timestamptz`
  в UTC (`DateTime(timezone=True)`, `datetime.now(UTC)`; ruff DTZ запрещает naive datetime).
  `created_at`/`updated_at` с `server_default=func.now()`.
- Деньги — `Numeric(38, 18)`, в Python `Decimal`. Валюта — `String(10)` с внешним ключом
  на справочник валют.
- Перечисления — `StrEnum` в Python и `String` + `CHECK` в БД (не PostgreSQL ENUM: его неудобно
  мигрировать).
- Инварианты дублируются ограничениями БД (UNIQUE, CHECK, FK), где это возможно.
- Изменение схемы: [../.agents/skills/db-migration/SKILL.md](../.agents/skills/db-migration/SKILL.md).

## API

- Схемы Pydantic v2. `Decimal` сериализуется в JSON строкой — это так и должно быть (M1).
- Формат ошибок (вводится с первым бизнес-эндпоинтом):
  `{"error": {"code": "insufficient_funds", "message": "..."}}`. Код ошибки машиночитаемый
  и стабильный, frontend опирается на `code`.
- Списки с пагинацией курсором или `limit/offset`, по умолчанию сортировка по `created_at desc`.
- Эндпоинты, создающие денежные операции, принимают заголовок `Idempotency-Key` (M5).

## Логирование

- `logger = logging.getLogger(__name__)`, никаких `print` (ruff T20).
- В сообщениях логов id сущностей, а не ПДн: `"order %s failed", order.id`.
- Никогда не логируй тела запросов к партнёрам и webhook целиком: только id, статус, код ошибки.

## Тесты

- pytest + pytest-asyncio (`asyncio_mode=auto`, общий event loop на сессию). Всё идёт
  на настоящем PostgreSQL.
- Фикстуры (`tests/conftest.py`):
  - `db_session` — сессия внутри внешней транзакции, которая откатывается после теста.
    `commit()` в тестируемом коде безопасен.
  - `engine` — для тестов с реальными коммитами и несколькими соединениями (конкуренция, M4).
    Такие тесты сами убирают за собой данные.
  - `app`, `client` — приложение с тестовыми настройками и `httpx.AsyncClient`.
- Внешние HTTP-вызовы подменяются через `httpx.MockTransport`. Сеть в тестах запрещена.
- Тестируй поведение через публичные функции сервиса или API, а не внутренности.
- Предупреждения считаются ошибками (`filterwarnings = error`). Чини причину, не глуши.
- Тесты идут в случайном порядке (pytest-randomly) и не должны зависеть друг от друга. Упавший
  порядок воспроизводится `uv run pytest --randomly-seed=<seed>` (seed печатается в начале вывода),
  для отладки порядок отключается `-p no:randomly`.
- `make backend-test` проверяет покрытие `app/` с ветками: не ниже 90%. Одиночный запуск
  `uv run pytest ...` идёт без проверки покрытия.
- Инварианты ledger (сумма проводок ноль, баланс равен сумме проводок) проверяются
  property-based тестами на hypothesis, библиотека подключается в T-02.
