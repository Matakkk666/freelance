# AGENTS.md

Главная инструкция для ИИ-агентов и разработчиков. Прочитай целиком перед любой задачей.
Для кода в `backend/` и `frontend/` есть свои `AGENTS.md` с деталями. Они дополняют этот файл,
а не заменяют его.

## Проект в двух словах

MVP финтех-сервиса с личным кабинетом: внутренний кошелёк (ledger с двойной записью), история операций,
подписки (Стандарт / Plus / Premium), реферальная программа, покупка продуктов партнёров
(eSIM, подарочные карты, позже криптокарты и VPN) через их API, базовая админка.
Мы не храним реальные деньги и не делаем блокчейн. Деньги лежат у криптопроцессинга
или кастодиального провайдера, у нас хранится учёт.

Архитектура: модульный монолит. Один backend (FastAPI), отдельный процесс фоновых задач
из того же кода, PostgreSQL, одно SPA (React), в котором есть и кабинет, и админка.

## Язык

- С владельцем проекта общаемся на русском. Документация (`docs/`, `AGENTS.md`, `README.md`,
  описания PR) пишется на русском.
- Код, идентификаторы, комментарии в коде, сообщения коммитов и логов пишутся на английском.
- Тексты интерфейса пока только на русском.
- Соответствие русских терминов именам в коде — в [docs/glossary.md](docs/glossary.md).
  Используй эти имена, не придумывай синонимы.

Скиллы (`.agents/skills/<name>/SKILL.md`, та же папка доступна как `.claude/skills`):

- `money-operation` — любое изменение, затрагивающее баланс, ledger, платежи, вознаграждения;
- `add-partner-integration` — новый адаптер внешнего сервиса или замена мока реальным API;
- `db-migration` — любое изменение схемы БД;
- `requirements-update` — владелец прислал дополнение к ТЗ, ответ заказчика или изменение планов;
- `ui-design` — любая работа с интерфейсом: экран, компонент, стили, тексты.

## Стек

- Backend: Python 3.12, FastAPI, SQLAlchemy 2 (async, asyncpg), Alembic, Pydantic v2,
  pydantic-settings. Менеджер зависимостей uv (`backend/pyproject.toml`, `backend/uv.lock`).
- БД: PostgreSQL 16. SQLite не используем нигде, в тестах тоже.
- Frontend: React 19, TypeScript 6.0, Vite 8, Vitest, Testing Library. Менеджер пакетов pnpm
  (`frontend/pnpm-lock.yaml`), Node 24.
- Качество: ruff (lint + format), mypy --strict, pytest, eslint (strictTypeChecked), prettier, tsc.
- CI: GitHub Actions ([.github/workflows/ci.yml](.github/workflows/ci.yml)) запускает `make check` на каждый PR.

TypeScript закреплён на `~6.0`, потому что typescript-eslint пока не поддерживает 7.x. Не обновляй его,
пока это не изменится.

## Команды

Все рутинные действия выполняются через `make` (список: `make help`). Не вызывай инструменты
в обход Makefile, если для действия есть цель.

| Команда | Что делает |
|---|---|
| `make setup` | полная идемпотентная настройка: PostgreSQL (Docker или apt), `.env`, зависимости, миграции |
| `make install` | зависимости по lock-файлам (`uv sync --locked`, `pnpm install --frozen-lockfile`) |
| `make db-up` | только PostgreSQL через docker compose |
| `make migrate` | применить миграции к `DATABASE_URL` |
| `make migration name="add ledger" rev=0002` | создать миграцию (autogenerate) |
| `make dev` | backend :8000 + frontend :5173 (Vite проксирует `/api` и `/health`) |
| `make dev-backend` / `make dev-frontend` | по отдельности |
| `make format` | автоформатирование и автофиксы |
| `make lint` / `make typecheck` / `make test` | по отдельности |
| `make check` | всё, что запускает CI. Должно проходить перед каждым PR |

Один тест: `cd backend && uv run pytest tests/test_health.py -k ok` или
`pnpm --dir frontend exec vitest run src/pages/HomePage.test.tsx`.

Зависимости: `cd backend && uv add <pkg>` (dev: `uv add --dev <pkg>`), `pnpm --dir frontend add <pkg>`.
Lock-файлы коммитятся вместе с изменением.

Полный стек в Docker: `docker compose up --build` (frontend http://localhost:8080, backend http://localhost:8000).

## Правила для денег (обязательные)

Нарушение любого из этих правил блокирует PR. Правила пронумерованы, чтобы на них ссылаться
в коде, тестах и PR, например `# M4`.

- **M1. Никакого float.** Суммы хранятся как `Decimal` в Python, `NUMERIC(38, 18)` в БД, строка
  в JSON и TypeScript (`"12.500000"`). Во frontend суммы не превращаются в `number`, арифметику
  над деньгами делает только backend. Точность задаётся валютой (USDT — 6 знаков). Квантование
  делается только через money-хелпер модуля ledger, режим округления `ROUND_HALF_UP`, если в
  задаче не сказано иное. Проверки: AST-тест `backend/tests/test_code_rules.py` запрещает `float`
  в `backend/app/`, eslint запрещает `parseFloat`.
- **M2. Баланс меняется только проводками ledger** через сервис ledger
  (`post_transaction` и производные). Никакой другой код не пишет в `accounts.balance` и таблицы
  ledger. Все проводки операции и обновление балансов выполняются в одной транзакции БД.
- **M3. Сумма проводок операции равна нулю** в каждой валюте. Это проверяется и в коде,
  и в БД (отложенный constraint trigger).
- **M4. Баланс пользователя не уходит в минус.** Счета блокируются `SELECT ... FOR UPDATE`
  в порядке возрастания id, чтобы не было дедлоков, плюс `CHECK (balance >= 0)` для счетов
  без `allow_negative`. Нужен тест с параллельными списаниями.
- **M5. Идемпотентность.** У каждой денежной операции (`ledger_transactions.idempotency_key`
  UNIQUE), каждого запроса к партнёру и каждого входящего webhook (UNIQUE по
  `(provider, external_event_id)`) есть ключ идемпотентности. Повтор возвращает результат
  первого вызова и не создаёт второе начисление. Повтор с тем же ключом, но другими
  параметрами — это ошибка.
- **M6. Внешние вызовы не делаются внутри транзакции БД.** Поток покупки такой: транзакция 1
  (заказ + резерв, commit) → запрос к партнёру → транзакция 2 (списание или снятие резерва).
  При таймауте или неизвестном ответе заказ получает статус `processing` и проходит сверку
  с партнёром. Автоматического возврата нет.
- **M7. Подпись webhook проверяется до любой обработки**: сравнение в постоянное время,
  проверка timestamp, если провайдер его даёт. Неподписанный или неверно подписанный запрос
  получает 401 и ничего не меняет. Сырое событие сохраняется.
- **M8. Секреты только в env** через `Settings` (`SecretStr`). Их нет в коде, миграциях,
  тестах (там только заведомо фейковые значения) и логах. ПДн (email, телефон, номера карт,
  документы) не логируются. Форматтер в `app/logging.py` маскирует их как страховка, а не как
  разрешение.
- **M9. Реферальные начисления и ручные корректировки** проходят только проводками ledger
  с указанием причины (`reason`) и инициатора (`created_by`). Прямое изменение балансов
  запрещено.
- **M10. Действия в админке пишутся в журнал аудита** (кто, что, над чем, значения до и после,
  когда, IP) в той же транзакции, что и само изменение.
- **M11. Тарифы, комиссии, функции тарифов и условия рефералки хранятся в БД** и меняются
  из админки. В коде нет цен и процентов. Начальные значения задаются seed-данными
  в миграции.
- **M12. Записи ledger неизменяемы**: никаких UPDATE и DELETE проводок. Ошибка исправляется
  обратной (сторнирующей) операцией.
- **M13. Каждое правило покрыто тестами** на настоящем PostgreSQL: сумма ноль, запрет минуса
  при конкуренции, повторный webhook, неверная подпись, аудит, отсутствие секретов в логах.

Если задача требует нарушить правило, остановись и спроси владельца.

## Интеграции с партнёрами

Каждый внешний сервис (криптопроцессинг, виджет обмена, eSIM, подарочные карты, криптокарты, VPN)
подключается через свой адаптер в `backend/app/integrations/<service>/`: интерфейс в терминах
нашего домена, мок и реальные клиенты. Провайдер выбирается переменной окружения
(`<SERVICE>_PROVIDER=mock`).

**API партнёров не выдумываем.** Реальный клиент пишется только по документации из
`docs/partners/<partner>/`. Если документации нет, делаем только интерфейс по нашим
потребностям и мок, а вопросы записываем в `docs/decisions.md`. Пошагово:
[.agents/skills/add-partner-integration/SKILL.md](.agents/skills/add-partner-integration/SKILL.md).

Тесты никогда не ходят в сеть: внешние вызовы подменяются через `httpx.MockTransport` или моки.

## Изменения ТЗ

ТЗ пополняется по ходу проекта. Когда владелец присылает новое требование, ответ заказчика
или изменение планов, сначала обнови документы по скиллу
[requirements-update](.agents/skills/requirements-update/SKILL.md), и только потом пиши код:

1. Исходный текст сохраняется как есть в `docs/client-input/`.
2. В `docs/requirements.md` требование получает постоянный ID `R-NN`, ссылку на источник
   и связанные задачи. ID не переиспользуются, отменённые требования не удаляются.
3. Ответы на открытые вопросы становятся решениями в `docs/decisions.md`.
4. Новая работа — новые задачи в `docs/roadmap.md`. Готовые задачи не переписываются:
   доработка оформляется новой задачей.
5. Если новое требование противоречит правилам M1–M13 или уже сделанному, остановись и спроси.

Код пишется только под требования, записанные в `docs/requirements.md`. Если в задаче
нужно что-то, чего там нет, это новое требование: спроси владельца, а не додумывай.

## Порядок работы

1. Возьми задачу из [docs/roadmap.md](docs/roadmap.md) или из сообщения владельца. Уточняй
   только то, что действительно блокирует работу. Остальное решай сам и записывай
   в `docs/decisions.md`.
2. Ветка от `main`: `<type>/<task-id>-<slug>`, например `feat/t02-ledger-core`.
3. Одна задача — один PR. Не смешивай с посторонним рефакторингом.
4. Коммиты в стиле Conventional Commits на английском: `feat(ledger): add post_transaction`.
5. Тесты пишутся вместе с кодом. Изменил поведение — обнови тест и объясни почему.
6. Перед PR: `make check` зелёный, документация обновлена (см. ниже).
7. PR заполняется по шаблону [.github/pull_request_template.md](.github/pull_request_template.md)
   на русском: что сделано, как проверено (только то, что реально запускалось), что не сделано,
   риски. Мержить можно после зелёного CI.

Что обновить вместе с кодом:

- новое или изменённое требование → `docs/requirements.md` и `docs/client-input/` (скилл `requirements-update`);
- новое решение или отступление от старого → `docs/decisions.md`;
- новый модуль, таблица, поток, фоновая задача → `docs/architecture.md`;
- статус задачи, новые задачи → `docs/roadmap.md`;
- новая переменная окружения → `app/config.py` + `.env.example` с комментарием;
- новый термин → `docs/glossary.md`;
- новое правило или исправленная владельцем ошибка → раздел «Журнал правил» ниже.

### Критерии готовности любой задачи

- Критерий готовности задачи из roadmap выполнен и проверен.
- `make check` проходит локально и в CI.
- Новые денежные операции покрыты тестами по правилам M1–M13.
- Миграции применяются и откатываются (`tests/test_migrations.py`).
- Документация обновлена, в `.env.example` есть все новые переменные.
- Для интерфейса: чеклист [docs/design.md](docs/design.md) §6 пройден, скриншоты в PR.

## Чего не делать

- Не ослаблять проверки ради зелёного CI: не удалять тесты, не понижать строгость mypy и eslint.
  `# type: ignore[...]`, `# noqa: ...` и `eslint-disable` допустимы только с конкретным кодом
  и комментарием, почему нельзя иначе.
- Не править миграции, уже попавшие в `main`. Только новые миграции.
- Не добавлять инфраструктуру «на вырост»: микросервисы, Redis, Celery, Kafka, GraphQL,
  event sourcing. Сначала запись в `docs/decisions.md` с обоснованием.
- Не добавлять зависимость, если задачу решает стандартная библиотека или уже подключённый пакет.
- Не коммитить `.env`, ключи, дампы БД, реальные ПДн.
- Не хардкодить цены, комиссии, лимиты и условия рефералки (M11).
- Не вызывать внешние сервисы из тестов.
- Не оставлять в коде TODO без задачи в roadmap.
