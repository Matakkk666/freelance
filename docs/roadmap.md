# Roadmap

Каждая задача — одна ветка и один PR. Задачи идут по порядку, если в колонке зависимостей
не сказано иное. У каждой задачи есть критерий готовности (DoD) в дополнение к общим критериям
из [AGENTS.md](../AGENTS.md#критерии-готовности-любой-задачи).

Статусы: ⬜ не начата · 🟨 в работе · ✅ готова.

Как брать задачу: прочитай описание, связанные разделы [architecture.md](architecture.md)
и [decisions.md](decisions.md), сделай ветку `<type>/<id>-<slug>` (например, `feat/t02-ledger-core`),
в PR поставь статус 🟨 или ✅. Если по ходу появилась новая задача — добавь её сюда.

## Этап 1

### T-01. Фундамент проекта ✅
Документы, AGENTS.md, каркас backend и frontend, конфиг через env, БД и первая миграция,
`/health`, стартовая страница, линтеры, тесты, `make check`, CI, setup-скрипт, docker-compose.
**DoD:** `make check` зелёный локально и в CI, backend и frontend запускаются, `/health` отвечает,
PR открыт.

### T-02. Ledger: ядро ⬜
Модуль `ledger`: `currencies` (seed USDT, 6 знаков), `accounts`, `ledger_transactions`,
`ledger_entries`, money-хелпер (квантование, `ROUND_HALF_UP`), `post_transaction` и производные
(`hold`, `capture`, `release`, `adjust`, `reverse`), создание счетов пользователя и системных счетов.
Триггер «сумма ноль» (deferred) и запрет UPDATE/DELETE проводок. Проверка баланса против проводок.
API пока нет. Пользователей ещё нет, поэтому `user_id` без FK, FK добавляется в T-03.
**DoD:** тесты на M1–M5, M9, M12: несбалансированная операция отклоняется и кодом, и БД;
параллельные списания (≥10 одновременных) не уводят баланс в минус; повтор с тем же ключом
не создаёт второй операции, а с другими параметрами падает; UPDATE проводки падает;
квантование и округление покрыты тестами.

### T-03. Авторизация и пользователи ⬜
`users`, `user_identities` (email + пароль), роли `user`/`admin`, регистрация, вход, refresh,
выход, `GET /api/v1/me`. При регистрации создаются счета ledger и реферальный код, принимается
`ref`-код (привязка — в T-09, здесь только сохранение). Rate limiting на вход и регистрацию.
Способ создать первого админа (CLI-команда). Формат ошибок API (D-017).
Frontend: роутер, страницы входа и регистрации, хранение токена, защищённые маршруты.
**DoD:** тесты регистрации, входа, неверного пароля, истёкшего токена, доступа без прав к admin-эндпоинту
(403); пароль и токены не попадают в логи (тест); e2e-сценарий в браузере: регистрация → вход → главная.

### T-04. Журнал аудита и каркас админки ⬜
Модуль `audit`, зависимость `require_admin`, `/api/v1/admin/users` (поиск, карточка, баланс,
операции), ручная корректировка баланса через ledger с причиной (M9) и аудитом (M10).
Frontend: раздел `/admin` с этими экранами.
**DoD:** корректировка создаёт проводку и запись аудита в одной транзакции (тест с откатом:
ошибка после проводки не оставляет ни проводки, ни аудита); обычный пользователь получает 403.

### T-05. Фоновые задачи ⬜
Таблица `jobs`, воркер `python -m app.workers` с `SKIP LOCKED`, повторы с экспоненциальной задержкой,
планировщик периодических задач, `ledger.verify_balances`. Сервис `worker` в docker-compose,
`make dev-worker`. Просмотр упавших задач в админке.
**DoD:** тесты: два воркера не берут одну задачу; упавшая задача повторяется и после
`max_attempts` получает `failed`; задача с истёкшим lock подхватывается снова.

### T-06. Пополнение через криптопроцессинг (мок) ⬜
Адаптер `integrations/processing` (интерфейс + мок), `deposits`, `webhook_events`,
эндпоинт webhook с проверкой подписи, начисление через ledger, сверка висящих пополнений.
Мок умеет «оплатить» инвойс (эндпоинт или команда только для `APP_ENV=local/test`).
Frontend: экран пополнения.
**DoD:** тесты M5 и M7: повторный webhook не начисляет второй раз; неверная, отсутствующая
или просроченная подпись → 401 без изменений; параллельные одинаковые webhook → одно начисление.

### T-07. Кошелёк и история операций ⬜
`GET /api/v1/wallet` (балансы available/reserved), `GET /api/v1/wallet/history` (пагинация,
понятные типы операций), frontend: главная с балансом, экран истории, хелпер форматирования сумм.
**DoD:** суммы проходят от БД до экрана строкой без потери точности (тест backend и frontend);
пользователь видит только свои операции (тест).

### T-08. Тарифы и подписки ⬜
`plans`, `plan_features`, `fee_rules` (seed: Стандарт / Plus / Premium), `subscriptions`,
покупка подписки с баланса, `get_entitlements`, `calculate_fee`, задача продления,
`past_due` → `expired`. Админка: редактирование тарифов, функций, комиссий с аудитом.
Frontend: экран тарифов и текущей подписки.
**DoD:** тесты: оплата создаёт проводку, повтор не списывает дважды; продление при нехватке
средств → `past_due`, после льготного периода → `expired`; изменение цены из админки
пишется в аудит и не требует изменения кода.

### T-09. Реферальная программа ⬜
`referral_codes`, `referrals`, `referral_rules`, `referral_rewards`; привязка при регистрации;
начисление по событиям (оплата подписки и др.) через ledger; холд через фоновую задачу.
Админка: правила, список вознаграждений. Frontend: код, ссылка, приглашённые, история.
**DoD:** тесты: самоприглашение запрещено; повторное событие не начисляет дважды;
начисление имеет `reason` и видно в истории обоих пользователей.

### T-10. Заказы и поток покупки ⬜
Модуль `orders`: каталог (кеш продуктов партнёров), `orders`, `partner_requests`,
поток резерв → партнёр → списание/снятие, статус `processing`, задача `order.reconcile`.
Общий тестовый адаптер для проверки потока. Админка: заказы в `processing`.
**DoD:** тесты сценариев: успех, отказ, таймаут → `processing` → сверка → `completed`/`failed`;
во время вызова партнёра нет открытой транзакции (тест); повтор запроса покупки с тем же
`Idempotency-Key` не создаёт второй заказ.

### T-11. eSIM ⬜
Адаптер `integrations/esim` (интерфейс + мок; реальный клиент — когда будет документация
в `docs/partners/`), каталог тарифов eSIM, покупка через T-10, выдача QR/данных активации.
Frontend: витрина eSIM, покупка, мои eSIM.
**DoD:** покупка через мок проходит end-to-end в браузере; данные активации видит только владелец.

### T-12. Подарочные карты и цифровые товары ⬜
Адаптер `integrations/giftcards` (интерфейс + мок), каталог, покупка через T-10, выдача кода.
Frontend: витрина, покупка, мои покупки.
**DoD:** как у T-11.

### T-13. Подготовка к запуску ⬜
Деплой (Docker Compose на выбранном хостинге), HTTPS, бэкапы БД и проверка восстановления,
сбор ошибок, базовые метрики и алерты (упавшие задачи, расхождение балансов, заказы в `processing`),
ревью безопасности, оферта и политика ПДн (от заказчика).
**DoD:** чеклист запуска пройден, восстановление из бэкапа проверено.
