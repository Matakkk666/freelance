# Требования

Нормализованный список требований заказчика. ТЗ пополняется по ходу проекта, поэтому:

- исходные тексты заказчика лежат без изменений в [client-input/](client-input/). Этот файл —
  их выжимка, и у каждого требования есть ссылка на источник;
- у каждого требования есть постоянный ID `R-NN`. ID не переиспользуются и не перенумеровываются:
  отменённое требование остаётся в таблице со статусом «отменено»;
- изменения вносятся по скиллу
  [requirements-update](../.agents/skills/requirements-update/SKILL.md), каждое изменение
  записывается в историю в конце файла.

## Цель

MVP финтех-сервиса с личным кабинетом пользователя. Почти все продукты предоставляют партнёры
через API. Наша задача — единый backend и интерфейс, который их объединяет. Цель — рабочий MVP
без лишней сложности, который можно запустить на реальных пользователях.

## Этапы

- **Этап 1:** R-01, R-02, R-03, R-05, R-06, R-09, R-10, R-11, R-12.
- **Этап 2:** R-04, R-07, R-08 (зависят от поставщиков; KYC не нужен, R-17).
- **После этапа 1:** EUR как вторая валюта (R-18).

Заказчик хочет запуститься через 1–2 недели (R-19). Что входит в первый запуск при таком
сроке, решает владелец (Q-20).

## Пока неизвестно

Названия поставщиков карт, eSIM и подарочных карт и доступ к их API, криптопроцессинг,
провайдер виджета обмена, кто и как делает VPN, юрисдикция, платформа (веб или Telegram
Mini App), вид и размер реферальных вознаграждений, объём первого запуска.
Решения должны оставлять эти варианты открытыми.
Вопросы и временные допущения — в [decisions.md](decisions.md#открытые-вопросы).

## Вне рамок MVP

Собственный блокчейн, хранение реальных средств у себя, микросервисы, мобильные нативные
приложения, мультиязычность интерфейса.
